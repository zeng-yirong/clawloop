# Nanoclaw：面向可验证 Agent 强化学习的轻量级交互框架

当前 Agent 强化学习的核心困难，并不只是让模型学会生成格式正确的工具调用，而是如何以较低成本构造一个**可交互、可扩展且可验证**的训练环境。
真实 Agent 系统通常包含文件系统、终端、长期记忆、插件、外部服务和多 Agent 协作等大量组件。
直接在这类系统中开展强化学习，一方面会引入网络状态、服务版本和历史记忆等不可控变量，使同一策略难以稳定复现；
另一方面，复杂运行时会显著放大并行 rollout 的资源成本与故障概率。
更重要的是，Agent 任务通常不存在唯一的正确行动轨迹：模型可能采用不同的搜索、编辑和执行顺序得到同样正确的结果，因此仅监督工具调用过程容易限制策略探索，而仅评价最终文字回答又无法判断环境是否被真正修改。

针对这一矛盾，我们构建了 Nanoclaw，一个面向工具使用强化学习的轻量级 harness。
其核心思想是将 Agent 训练抽象为“**任务描述—通用工具—隔离环境—结果验证**”四个最小组成部分。
对于每条任务，框架创建一个独立工作区，模型通过多轮工具调用观察并修改环境，任务结束后由 verifier 直接检查最终工作区并产生奖励。
该设计将奖励对象从自然语言回答转移到真实环境状态：只要模型最终完成了任务，就可以获得正向反馈，而不要求其复现预先规定的操作路径。
由此，Nanoclaw 在保持奖励可自动验证的同时，为模型保留了搜索、试错、自我修正和工具组合的策略空间。

在交互范式上，Nanoclaw 采用 **ReAct（Reasoning and Acting）架构**，将模型行为组织为“思考—行动—观察”的循环：
在每次调用工具之前，模型先以文本形式分析当前任务状态、明确局部目标并选择下一步行动；
工具执行后，真实的环境反馈再次进入上下文，成为下一轮推理的依据。与同样具有环境交互、但根据当前 observation 直接生成工具调用的 action-only 模式相比，ReAct 在行动之前增加了显式的推理环节，使工具选择建立在对任务目标、已有证据和潜在风险的综合判断之上。
对于长程任务，这种机制有助于维持跨步骤计划、解释工具调用的目的，并在文件内容、命令输出或测试结果与预期不一致时重新评估和修正策略。因此，Nanoclaw 训练的不只是“何时调用哪个工具”，还包括如何依据环境状态形成计划，以及如何利用执行反馈持续调整后续行动。

Nanoclaw 的第一项关键特点是**以最终状态为中心的可验证训练机制**。传统对话式奖励容易偏向语言表面质量，过程级工具监督又需要昂贵的轨迹标注；Nanoclaw 则把文件内容、目录结构、程序输出和测试结果等可执行状态作为任务完成证据。验证器只判断目标是否实现，而不约束实现过程，从而缓解 Agent RL 中“开放式行动轨迹与确定性奖励”之间的冲突。
第二是**任务语义与 Agent 运行时解耦**：不同任务共享同一组基础工具和交互协议，任务差异仅由自然语言指令、初始工作区和结果验证规则表达。新增任务无需为模型设计专用动作空间，因此训练能力更容易迁移到未见过的文件结构、任务表述和工具组合中。

第三项创新是**面向大规模 rollout 的最小状态设计**。每条轨迹拥有独立工作区，不共享中间文件和长期记忆，避免并发采样之间的状态污染与训练数据泄漏；工作区本身又是可复制、可比较和可回放的显式状态，便于复现失败轨迹并分析策略行为。框架复用 VERL、Ray 和 vLLM 已有的分布式训练与推理能力，只实现环境交互和验证所需的薄层。相较于 OpenClaw、Hermes 等更强调完整 Agent 运行体验的重型系统，Nanoclaw 不承担用户管理、消息渠道、长期记忆、插件生态或复杂编排等产品功能。这种轻量化并非简单减少工具数量，而是主动消除与策略学习无关的隐藏状态，使训练中的变化尽可能来自模型策略本身。

框架的泛化能力主要来自三个方面。首先，模型使用的是读取、搜索、编辑和命令执行等领域无关的原子工具，而不是面向单一 benchmark 的任务专用 API；其次，最终状态奖励允许多种正确解法共存，使模型能够学习“观察—规划—执行—检查—修正”的一般性闭环；最后，任务定义、环境构造和验证逻辑彼此分离，同一套 harness 可以承载代码修改、配置处理、结构化数据编辑、文档操作和轻量系统任务。这里的泛化并不依赖扩大框架本身的功能，而是通过稳定的交互接口承载不断变化的任务与环境。

提示词设计同样遵循最小化原则。系统提示词只规定通用执行协议，例如限定在当前工作区内操作、先观察后修改、优先进行最小且正确的改动、在完成后停止调用工具，并明确最终奖励取决于工作区状态而不是答案措辞。提示词不注入特定任务的解题步骤，也不包含复杂人格、产品功能或长期记忆规则，从而减少无关先验对策略探索的干扰。模型所需的任务知识由用户指令和当前环境提供，工具调用格式则通过 parser 与模型解耦，因此可以适配 Qwen3-Coder 格式，也可以进一步替换为其他工具调用协议。

下面给出一个简化示例。系统提示词只声明通用执行规则，用户要求修改一个配置项；交互中的 `Thought` 是工具调用前显式生成的文本思考，`Observation` 则来自真实工作区。该示例使用抽象格式表示交互过程，不绑定具体的 tool-call parser。

```text
System: 在当前工作区内完成用户任务。先检查相关文件，再进行最小且正确的修改；
        根据工具返回结果继续行动。

User: 将 config.yaml 中的 max_retries 修改为 5，其他配置保持不变。

Thought: 我需要先读取文件，确认字段当前位置和当前值，避免覆盖其他配置。
Action:  read_file(path="config.yaml")
Observation: max_retries: 3
             timeout: 30

Thought: 目标字段存在，只需要进行一次局部替换，然后重新读取文件确认结果。
Action:  edit_file(path="config.yaml", old="max_retries: 3", new="max_retries: 5")
Observation: Edit succeeded.

Thought: 修改已经执行，我需要检查最终状态是否符合要求。
Action:  read_file(path="config.yaml")
Observation: max_retries: 5
             timeout: 30

Final: 配置修改完成。
Verifier: 检查 max_retries == 5 且其他配置未改变，返回奖励 1。
```

这一示例体现了 ReAct 与直接工具调用的差别：模型并非只连续输出 `read_file` 和 `edit_file`，而是在每个行动前说明当前证据、局部目标和工具选择依据；每次工具返回的 observation 又会改变下一轮思考。训练奖励最终仍由环境结果决定，因此显式推理用于辅助规划与纠错，而不是替代可执行验证。

Nanoclaw 使用一组紧凑但覆盖完整工作流的工具，其与 Codex 能力的对应关系如下：

| Nanoclaw 工具 | 主要功能 | 对应的 Codex 能力 |
|---|---|---|
| `list_dir` | 查看目录与文件 | `exec_command` 中的 `ls` 或 `rg --files` |
| `read_file` | 读取文件内容 | `exec_command` 中的 `sed`、`head` 等只读命令 |
| `write_file` | 创建或完整写入文件 | `apply_patch` 新增文件 |
| `edit_file` | 定位并替换已有内容 | `apply_patch` 更新文件 |
| `apply_patch` | 对一个或多个位置进行补丁式修改 | Codex 的 `apply_patch` |
| `grep` | 搜索文件内容 | `exec_command` 中的 `rg` |
| `find` | 按名称或模式查找文件 | `exec_command` 中的 `rg --files` 或 `find` |
| `mkdir` | 创建目录 | `exec_command` 中的 `mkdir` |
| `bash` | 执行受限命令、脚本或测试 | Codex 的 `exec_command` |

总体而言，Nanoclaw 所解决的关键问题是：如何在不引入完整产品级 Agent 系统复杂度的前提下，为强化学习提供真实的多轮工具交互、开放的策略空间和可靠的自动奖励。其创新性不在于构造更多专用工具，而在于以隔离工作区统一环境状态，以通用工具统一行动空间，以最终状态验证统一奖励接口，并以轻量 harness 将三者接入分布式 RL 训练。该设计为可复现、可扩展的 Agent RL 提供了一个更清晰的实验边界，也使模型学习的重点从适应某个重型框架，转向获得可迁移的环境操作与问题求解能力。
